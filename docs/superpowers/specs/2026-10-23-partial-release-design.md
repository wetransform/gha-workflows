# Partial releases from a release branch — design

## Intent

Our repos release by running the managed **Release** workflow on the default branch. semantic-release
derives the version from conventional commits since the last tag, writes `CHANGELOG.md`, creates a
release commit and tag, publishes artifacts and creates the GitHub release.

QA tests builds of the default branch, deployed to one shared test environment (per-change environments
are not feasible across the platform). So the default branch regularly contains a mix of:

- changes QA has accepted,
- a merged feature still waiting for QA,
- a change that went through QA, failed, and needs more work.

When the accepted changes must ship, the branch as a whole can't be released. So far this was worked
around by keeping unready changes off the branch or by rushing QA on everything; neither is always
possible.

We want a way to release **only selected changes** without breaking versioning or the changelog, both
for the release itself and for the next regular release from the default branch.

This is expected to be **rare**. Regular releases from the default branch remain the normal path and
must not change.

## Goals

- A person can release a chosen subset of the default branch's changes. Two cases must work:
  - **Prefix:** the changes to ship are all older than the unready ones → release the default branch
    as of an earlier commit.
  - **Interleaved:** an accepted change sits after an unready one → the unready one is left out.
- The partial release has a correct version and a changelog that lists exactly what shipped.
- Afterwards the default branch knows about that release: its next regular release gets the next
  correct version, and its changelog lists the held-back changes (once) and nothing that already
  shipped.
- Works for repos using the `gradle-service` and `gradle-library` shared workflows.

## Non-goals

- Other project types (sbt, play, mise, dockerfile, gha). They share the same semantic-release
  assumptions and may follow later; nothing here should make that harder.
- Per-change test environments, or any change to how QA works.
- Feature flags.
- Deciding *which* changes are safe to ship together. Shipping a combination QA never saw as a whole is
  acceptable in principle — it's the judgment of the person doing the release.
- A one-click UI that builds the release branch from inputs. Creating the branch by hand is fine.

## Anti-goals (would be a failure even if it technically works)

- Regular releases from the default branch behave differently or need extra steps.
- A changelog entry appears twice, or a held-back change silently never appears in any changelog.
- A version is produced that collides with an existing or future default-branch version.
- The default branch is left without the held-back changes because someone forgot a manual step.

## Current state (as found)

- Repos have a managed caller workflow `.github/workflows/tf-release.yml` (generated by
  `github-bootstrap` from `workflow-templates/release.gradle-{service,library}.tfpl.yml`), triggered by
  `workflow_dispatch` (and on push to the default branch for repos with `automatic_release`).
- It calls `gha-workflows/.github/workflows/gradle-{service,library}-publish.yml`, which uses
  `gradle-{service,library}.yml`, which uses the action `wetransform/gha-gradle-semantic-release`.
- That action, if the repo has no `.releaserc.yml`, generates one with
  `branches: ${{ github.head_ref || github.ref_name }}` — i.e. **whatever branch the workflow runs on is
  treated as the release branch**, with versions computed from tags reachable from it. Plugins:
  commit-analyzer + release-notes-generator (preset `conventionalcommits`), changelog, exec (gradle
  publish), git (commits `CHANGELOG.md`), github.
- semantic-release pushes using the **we-release** GitHub App token. That app is a bypass actor
  (`always`) for the "Require PR and status checks" ruleset. The "Protect default branch" ruleset only
  forbids deletion and non-fast-forward pushes.
- Repos only allow **rebase** merges for PRs (no merge commits, no squash).
- gradle-service publish tasks also push `:latest` Docker images (and so does the Publish workflow on
  every default-branch push).

## Decided approach

### The flow

1. **Person:** create a branch from the default branch at the newest commit that contains everything to
   ship (any branch name). For each change that must not ship and is contained in the branch, run
   `git revert <sha>` (one revert commit per original commit; keep git's generated message). Push.
2. **Person:** run the existing Release workflow on that branch (`workflow_dispatch`, branch selector).
3. **semantic-release** releases the branch as it does today. Because both a commit and its revert are in
   the release range, the `conventionalcommits` parser's revert handling should drop both from the
   version calculation and the release notes. *To be verified* (see Verification).
4. **Bot (new):** after a successful, non-dry-run release from a branch that is **not** the default
   branch:
   1. Merge the release branch into the default branch with a **real merge commit** (so the release tag
      and changelog commit become reachable from the default branch) and push it with the we-release
      app token. Rebase/squash would rewrite the release commit and lose the tag link — not acceptable.
   2. **Re-add (default on, can be disabled):** for every revert commit in the release branch (commits
      between the branch point and the release commit whose message matches git's
      `This reverts commit <sha>.`), add a commit on the default branch that re-applies the reverted
      change, using the **original commit's message** (so it counts as `feat:`/`fix:` etc. in the next
      release). Push together with the merge.

Result: the default branch contains the release commit + tag (next regular release starts from it),
the reverts and their re-applies cancel out in code, and the re-applied commits are new commits after
the tag, so the held-back changes are released and listed by the next regular release.

### Why reverts and not cherry-picks

Cherry-picking accepted changes onto a branch cut from the last tag would give them new SHAs; the
originals on the default branch would stay outside the tag's history and appear again in the next
changelog (and could affect the bump). Reverting keeps the shipped commits identical to the default
branch's, so ancestry stays correct.

### Re-add opt-out

- New boolean input on the Release workflow in the templates
  `github-bootstrap/workflow-templates/release.gradle-service.tfpl.yml` and
  `release.gradle-library.tfpl.yml` (e.g. "Re-add reverted changes on default branch", default `true`),
  passed down through `gradle-{service,library}-publish.yml` → `gradle-{service,library}.yml` → wherever
  the merge-back lives. Adding an input to the managed templates is fine.
- Only relevant for releases from non-default branches; ignored otherwise.

### Safety checks (my call — please check)

- **Before releasing from a non-default branch:** fail early unless the branch contains the default
  branch's latest release tag. A branch cut before the latest release would compute versions that can
  collide with the default branch.
- **Merge-back failure** (e.g. conflict, or the default branch moved and the push is rejected): the
  release itself stays as is. The workflow fails loudly and the log/summary states clearly what is left to
  do (exact git commands to merge back and re-add by hand). Retrying the push after re-fetching when the
  default branch merely moved is up to the builder.
- **Automatic-release repos:** the bot's push to the default branch must **not** trigger an automatic
  release (the re-added `feat:`/`fix:` commits would otherwise be released immediately). Do **not** use
  `[skip ci]` for this: it would also skip the regular Publish/check workflows on the default branch
  (snapshot, `:latest`, test environment), which must keep running. Instead the Release path recognises
  the bot's merge-back push (mechanism up to the builder) and skips only the release. *(my call)*
- Dry runs: no merge-back.

### Nice-to-haves (do if cheap; otherwise document as known limitation and defer)

- **No `:latest` from a partial release (gradle-service):** a release from a non-default branch pushes
  only the versioned image, not `:latest` (e.g. drop `dockerPushLatest` from the release tasks in that
  case — the action already distinguishes `release-tasks` from `publish-tasks`). Reason: the shared test
  environment should not briefly lose held-back changes. The regular default-branch release keeps
  pushing `:latest` as today.
- **Block regular releases while a merge-back is pending:** before releasing from the default branch,
  refuse (with a clear message) if a release tag exists that is newer than the latest tag reachable from
  the default branch and is not itself reachable — i.e. a partial release whose merge-back failed. This
  is the only accepted change to the regular path, and it only triggers in that error case. Reason:
  otherwise the next (possibly automatic) default-branch release would recompute the same version and
  leave a broken release commit.

## Constraints

- Regular default-branch releases must be untouched in behaviour (sole exception: the pending-merge-back
  guard above).
- The release branch runs the Release workflow version pinned in the commit it was cut from; partial
  releases only work for branches cut after the repo picked up the new workflow version.
- Use the existing we-release app token for pushes; no new secrets or bypass actors.
- Keep using the generated `.releaserc.yml` path (repos with their own `.releaserc.yml` keep working as
  today; merge-back may apply to them too if it doesn't depend on the generated config).
- Changes ship as new versions of `gha-gradle-semantic-release` / `gha-workflows`, and updated templates
  in `github-bootstrap` (versions pinned by SHA as today; renovate updates the pins).
- Conventional commits for all changes (see user conventions).

## Verification

- Test project: `wetransform/exp-gradle-release` (gradle-library). Releases can be created there freely.
- Must demonstrate, with real releases:
  1. Prefix case: branch at an older commit → release → merge-back → next default-branch release has the
     right version and a changelog without duplicates.
  2. Interleaved case: branch with a `git revert` of an unready `feat:` while a later `fix:` stays →
     patch release whose notes list only the fix → merge-back with re-add → next default-branch release
     is a minor bump listing the feature exactly once.
  3. Re-add disabled → reverted change stays off the default branch.
  4. Guard: branch not containing the latest tag is refused.
  5. Regular default-branch release unchanged.
- gradle-service path: at least a dry run / review that the same mechanism is wired in.

## Left to the builder

- Where the merge-back logic lives: inside `gha-gradle-semantic-release` (shared by both workflow types)
  is the natural place; a separate step/job in `gha-workflows` is acceptable if there's a reason.
- Exact input names, log/summary wording, retry behaviour.
- How revert commits are detected and mapped to originals (git's standard message is the contract).
- How to stop the merge-back push from triggering automatic releases.
- Documentation for people doing a partial release (short how-to, e.g. in the `gha-workflows` README):
  create branch, `git revert` each unready commit including its follow-up fixes, don't edit the revert
  message, don't use `--no-commit`, run Release on the branch.
